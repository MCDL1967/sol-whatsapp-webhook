## Resolved — venue_id Resolution (narrow fix)

`reservation_details.venue_id` was null for every reservation (real or seeded) because the `venues` table was empty and `supabase_bridge/supabase_client.js` had no lookup logic — it stored the venue name as workaround text in `special_requests` instead. Scoped narrowly, not the full architecture (see "Open" below):

| Item | Decision |
|---|---|
| Venue seed data | 6 real venues seeded for the `demo` property, sourced from `property_packages/demo/property_master_data.json`'s `dining.venues` list (excludes Room Service — already decided as a service, not a venue). `display_name` values match `webhook.js`'s `KNOWN_RESERVATION_VENUES` canonical strings exactly, since that registry already collapses guest text to one of a fixed set of names before anything reaches Supabase. Applied via direct `supabase-py` upsert, not `supabase db push --include-seed` — that path silently no-ops without Docker running locally (confirmed: it updates the tracked seed hash without executing the SQL). `supabase/seed.sql` was still updated with the equivalent SQL for documentation/future-Docker-availability, but treat the live database, not that file, as source of truth until re-verified with Docker running. |
| `venue_aliases` | Explicitly **not** seeded. Would be inert: `webhook.js`'s alias/typo matching happens entirely before `venue_or_department` ever reaches Supabase (a typo that doesn't match `KNOWN_RESERVATION_VENUES` today stays `null` before and after this fix — no regression, no improvement). Seeding aliases now would be accurate but unused data until the full runtime-package architecture (see "Open" below) actually queries it. Revisit together with that work, not before. |
| `supabase_bridge/supabase_client.js` lookup | Exact-match query (`venues.display_name = payload.venue_or_department`) at write-time, soft-fail internally (catches its own errors, returns `null` on any failure — never blocks the reservation write). `reservation_details.special_requests` changed from the venue-name workaround text to `null`, since no real guest "special requests" capture exists anywhere in the current conversation flow. |
| LOGS dashboard | `logs_app.py`'s `CASE_SELECT` now embeds `reservation_details(*, venues(display_name))`; `list.html`/`detail.html` show the resolved venue name, falling back to the old `special_requests` text only for rows written before this fix (their `venue_id` stays permanently null — not retroactively fixed). |
| Verification | No Node.js installed locally (confirmed: not found anywhere in PATH or standard install locations) — `webhook.js` has apparently never been run locally, only on Render. Verified via commit + deploy + live WhatsApp test instead of local execution. |

Idempotency note: tables whose natural unique key includes a nullable `language` column (`venue_aliases`, `menu_option_aliases`, `menu_branch_triggers`) can't rely on `upsert(on_conflict=...)` — Postgres treats distinct rows with `NULL` in that column as non-conflicting, so re-running would duplicate them. The script instead deletes-then-reinserts those tables scoped by `venue_id`/`branch_id`, making the whole script safely re-runnable. Same reasoning applied to `answer_boundaries`, which has no natural unique key at all.

## Resolved — Menu Tree Ownership Conflict (2026-07-27)

The 2026-07-05 v0.3 review round had accepted "menu structure stays SOL/Admin-owned, keep full menu tree editing out of the tool." The 2026-07-22 session then said the opposite ("tenant should be able to add further branches") without the conflict being caught at the time. Flagged in the 2026-07-22 handoff doc as blocking mockup-tool design; resolved this session before starting that tool.

| Item | Decision |
|---|---|
| Options considered | (1) old v0.3 boundary holds as-is — no structural editing at all; (2) hybrid — tenants can add options within existing branch types but not new top-level branches; (3) full tree-authoring — tenants can add/rename/remove branches and options, not just fields. **(3) chosen.** |
| Starting structure | Each tenant's tree starts as a generic structure modeled after the demo property's existing branch/option shape — not a blank tree. |
| Tenant capability | Rename or remove any branch/option; add new branches (including new top-level conversation categories) and new options within any branch. |
| Depth/breadth limits | Needed because unbounded trees threaten both the graph-walker/back-navigation logic and WhatsApp's interactive-list UI, which hard-caps at 10 rows per list message. Limits are **SOL/Admin-owned and per-tenant configurable** (a future product-owner control, not yet built) — not a single hardcoded global constant, and not tenant-editable. Starting default for new tenants: **max depth 4 levels below `main_menu`, max 10 children per branch.** For reference, the demo property today uses depth 2 and a widest branch of 7 options, so the defaults leave headroom. |
| Downstream effect | Confirms the generic-graph-walker rewrite (section 3.8 of `SOL_DB_Master_Plan_v1.0.md`) is still justified — tenants really will add branches the hardcoded `fast_path_*.js` `if` blocks don't know about. |
| Not yet built | The per-tenant depth/breadth limit control itself (who sets it, where it lives — likely a new column/table, SOL/Admin RLS-scoped) has no schema yet. This is new surface for the Tenant Property Configuration Tool build to define, not something migrated from existing data. |

## Resolved — Team Routing Generalized to Arbitrary Per-Tenant (2026-07-28)

Prompted by adding "Teams" to the Tenant Property Configuration Tool: the original 3 teams' backend keys were semantically named (`fnb_team`/`sec_team`/`ops_team`) and case routing (`dept_target`) was a fixed `check (dept_target in ('FNB','SEC','OPS'))` constraint on both `teams` and `cases` — meaning a 4th tenant-added team had nowhere to route. Resolved: routing becomes fully arbitrary per-tenant (not shared fixed buckets), because each tenant will eventually get their own LOGS login and isn't sharing routing buckets with anyone else.

| Item | Decision |
|---|---|
| Migration | `supabase/migrations/20260728120000_generalize_team_routing.sql` — dropped the `dept_target` check constraint on both `teams` and `cases` (found and dropped by querying `pg_constraint` rather than guessing the auto-generated constraint name), and renamed the 3 existing teams' `team_key` from `fnb_team`/`sec_team`/`ops_team` to generic `team_1`/`team_2`/`team_3` (`display_name`/`id` untouched). Applied via `supabase db push --linked` and verified live (rename confirmed, and a test insert with an arbitrary `dept_target` value succeeded where it previously would have violated the constraint). |
| `dept_target` going forward | Vestigial. Still `NOT NULL` on both tables (not dropped — a column drop is a bigger, less reversible move than this needed), auto-set to mirror `team_key` on every new row, no longer read by any live routing or display code. |
| Real routing mechanism | `teams.team_key`/`display_name` + `cases.assigned_team_id` (an FK to `teams.id` that already existed in the schema but nothing ever wrote to before this — confirmed via grep that neither `logs_seed.py` nor `supabase_client.js` set it). |
| `tenant_tool` | New `POST /teams/add` route — computes the next generic `team_N` key from existing rows, tenant supplies only the display name. `team_key` itself stays SOL/Admin-generated, never tenant-editable, consistent with the existing ownership split. |
| `logs/` rewrite | `logs_app.py`'s 4 hardcoded routes/views (`/gm /fnb /sec /ops`) became 2: `/gm` (unchanged — "GM sees every case" was already independent of `dept_target`) and one dynamic `GET /team/<team_key>` generated from the live `teams` table. `_counts()` now returns a `by_team` dict instead of hardcoded `fnb`/`sec`/`ops` keys. `base.html`'s nav is now a loop over teams. `list.html`/`detail.html`: removed the `dept_target` filter dropdown (dead code even before this — `_get_cases` never actually read `filters["dept_target"]`, only the route's fixed positional argument, so the dropdown never did anything) and the per-row/per-case `dept-badge` (its CSS classes were keyed to the fixed 3 depts and don't generalize); the `team_id` filter dropdown and the existing `c.teams.display_name` "assigned" column already covered the same job generically and needed no changes. `list.html`'s per-case-type columns (Location, Venue/Notes, Service Date) are now always shown instead of gated by which fixed department view you're on, since a team is no longer assumable to mean one specific case type. |
| `logs_seed.py` | Seeded teams renamed to `team_1`/`team_2`/`team_3` (kept their flavorful `display_name`s). Every seeded demo case now sets `assigned_team_id` (resolved via a seed-script-local `dept_target`→`team_key` grouping label, used only inside the seed script, never written to the real column) — previously every case, seeded or real, had `assigned_team_id` null, so the "assigned" column in LOGS showed "Unassigned" for 100% of existing data despite being fully wired. |
| `supabase_client.js` reservation writes | Was hardcoding `dept_target: "FNB"` on every reservation case, which became actively wrong once team keys stopped being semantically named. **Checked and confirmed `venues.handoff_team_key` was never a real column** — it only ever existed in the source JSON (`property_master_data.json`) and old planning-doc proposals (the `Physical_Schema_v0.1.md` `venues` table has no such column). Rather than guessing a team or rushing in a new column/backfill/UI mid-pass, chose to leave new reservation cases `assigned_team_id: null`, `dept_target: "unrouted"` — visibly unassigned in LOGS, not silently wrong. |
| Follow-up flagged, not yet built | A real `venues.handoff_team_key` column (or equivalent) plus tenant_tool UI to set it per venue, so reservation cases can actually auto-route to a team. Blocks nothing today since it was already non-functional before this change. |

## Resolved — Venues Section Built, Venue Keys Generalized (2026-07-30)

Added the Venues section to the Tenant Property Configuration Tool, the same CRUD pattern as Teams (per-venue form, hard-delete-if-unused / soft-delete-if-referenced, generic-key add). Two decisions along the way:

| Item | Decision |
|---|---|
| Field mapping | Real schema fields only, matching the old mockup's venue-card fields 1:1 where a real column exists: `display_name` (guest-facing name), `venue_type`, `reservation_enabled`, `selectable`, `show_in_restaurant_list`, `venue_aliases` (comma-separated in the UI, delete-then-reinsert on save), `venue_descriptions` (English `short_description` only, upserted on the `(venue_id, language)` PK). Deliberately **not** mapped: the mockup's `cuisine_or_service_type`, `handoff_team_key`, `group_reservation_supported`, and `escalation_note` fields have no backing column in the real schema — inventing new columns for a "quick pass" wasn't in scope, so those stayed out rather than being faked. Structured `venue_hours` (day-of-week rows) also stayed out — the mockup only ever had a single free-text hours field, which doesn't map to the real per-day schema; flagged as its own future pass, not solved here. |
| Delete safety | Same two-tier pattern as Teams: 0 reservations referencing the venue → hard delete (also explicitly clears `venue_aliases`/`venue_descriptions` first, since neither has `ON DELETE CASCADE` — confirmed by reading the migration SQL directly, a real FK violation risk if skipped). ≥1 reservation → soft delete (`active = false`), key stays reserved. |
| Venue key generalization | Migration `supabase/migrations/20260730120000_generalize_venue_keys.sql` renamed the 6 existing venues' descriptive `venue_key`s (`fenicia`, `la_brasserie`, ...) to generic `venue_1`..`venue_6`, matching the same treatment teams got — same reasoning (tenant doesn't need to know the internal identifier), extended for consistency once newly-added venues would otherwise get clean `venue_N` labels while the original 6 kept showing raw slugs. Verified safe before running: grepped for these key strings outside the `venues` table — the only hits were in `webhook.js` and `property_packages/demo/*.json`, both part of the separate, still-disconnected static-file system (confirmed elsewhere this session `webhook.js` doesn't read Supabase's `venues.venue_key` at all; live venue matching goes through `display_name`). `display_name`/`id` untouched, applied via `supabase db push --linked`, confirmed live both via direct query and via the rendered `tenant_tool` page. |

## Resolved — Real Per-Venue Team Routing (2026-08-03)

Closes the gap flagged in the previous section's "Follow-up flagged, not yet built" row — reservation cases could now actually auto-route to a team.

| Item | Decision |
|---|---|
| Column | `supabase/migrations/20260803120000_add_venue_handoff_team.sql` — added `venues.handoff_team_id` (uuid, FK -> `teams.id`). Deliberately **not** named `handoff_team_key` (the old source-JSON/planning-doc name, never a real column) — built as a real FK instead, matching `cases.assigned_team_id`'s already-established pattern rather than reintroducing a loose, unvalidated text key. |
| Backfill | Every venue defaulted to whichever team is "Guest Services" — matching exactly what the old source JSON quietly did (`handoff_team_key: "team_name_1"` on every venue, and `team_name_1` = Guest Services = originally `ops_team` = renamed `team_3` in the team-routing migration). Verified live post-migration: all 6 venues correctly point at the Guest Services team. |
| `tenant_tool` | Venues form gained a "Handoff team" dropdown, populated live from that property's real `teams` table (not hardcoded) — same dynamic-list pattern the app already used elsewhere. Confirmed via the app's own rendered HTML that Fenicia's dropdown pre-selects "Guest Services," matching the backfilled data. |
| `supabase_client.js` | `resolveVenueId` became `resolveVenue` — same soft-fail-never-blocks-the-write pattern, but now also returns the venue's handoff team (`teams(team_key)` embedded in the same PostgREST query, confirmed live via `supabase-py` against the same REST layer before trusting the untestable-locally JS side — no Node.js installed). Venue resolution moved to *before* the case insert (was previously resolved only for `reservation_details.venue_id`, after the case row already existed) so the case can be written with the right `assigned_team_id`/`dept_target` in one shot. A venue with no configured handoff team (or that doesn't resolve at all) still falls back to `dept_target: "unrouted"`, `assigned_team_id: null` — visible, not guessed. |
