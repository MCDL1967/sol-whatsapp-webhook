One-line fix: `reservation_name: payload.guest_name`.
  - **Fixed: `venues.show_in_restaurant_list` was fully inert.** Compiled into `runtime_packages.package_json` by `compile_runtime_package.py` but never read by `fast_path_classifier.js`/`fast_path_responder.js` — toggling it off in `tenant_tool` (intended use: a venue closed for remodeling, without deleting it) had zero guest-facing effect. Now wired via a new shared module, `src/fast_path/visible_options.js` (`getVisibleNumberedOptions`/`isVenueHidden`), used by both the classifier and responder so they can't drift on what a typed number resolves to: a hidden venue's option is excluded from the printed list, from numeric matching, and from label/alias matching, and the remaining options renumber contiguously (1, 2, 3, ...) rather than skipping the hidden slot's original number.

Worse, undetected until a dry-run check: Garden Lobby Bar's stale `"5"` alias would have silently out-resolved Fenicia's new, correct position-5 the next time a guest typed `5` — a wrong-venue match, not just a redundant one. Fixed in `fast_path_classifier.js`: legacy numeric-variant alias rows (digit, `#digit`, `option N`, `opcion N`, spelled-out numbers) are now skipped entirely when building the match index, leaving the dynamic renumbering as the sole source of truth for numeric matching. **The underlying `menu_option_aliases` rows were not deleted** — only the classifier's runtime trust in them changed.
  - **Flagged, not built: Voiceflow has no awareness of `show_in_restaurant_list`.** The fast-path classifier correctly refuses to match a hidden venue's name (confirmed live: typing "Larry's Sports Bar & Terrace" produced no `[FAST PATH HIT]`), but the message then falls through to Voiceflow as plain text, and Voiceflow's own reservation-detection logic has no cross-check against venue availability — it processed a full reservation flow for the hidden venue anyway. `webhook.js` already injects bracketed context into Voiceflow's payload for other things (`[[RESTAURANT CONTEXT: ...]]`, `[[SESSION LANGUAGE LOCK: ...]]`); the same mechanism could carry a list of currently-unavailable venues for Voiceflow to decline against, but needs its own design pass (what to inject, when, how it interacts with a venue the guest already picked earlier in conversation) before being built. See section 9.
  - Not yet committed/pushed as of this writing — held at the reporter's request pending further local compile testing.

## 2. Architecture overview

```text
Tenant Property Configuration Tool (tenant_tool/ — live; Overview, Basics,
  Teams, Venues, Guest Rules, Menu Tree, Review & Export built; Response
  Templates, Answer Boundaries still missing)
  -> normalized Supabase config tables
  -> compile step (logs/compile_runtime_package.py — still a manual script,
     not triggered automatically by Publish)
  -> runtime_packages.package_json
  -> fast_path_classifier.js / fast_path_responder.js / property_loader.js
     (rewired 2026-08-10 -- generic, reads the compiled package, in-memory
     cached; see section 1). Full standalone "SOL Menu Runtime Service" per
     section 4 was not built as a separate thing -- its responsibilities
     landed as this generic rewrite instead.
  -> webhook.js -> WhatsApp

Operational guest activity (already live, unaffected by any of the above):
  guest_threads -> messages -> cases -> case detail tables -> operational_events -> LOGS
```

Key principle carried forward from the original v0.3 review round and reconfirmed this session: **the normalized DB is the source of truth for editing/governance; the compiled package is the fast, cached read model for guest turns.** Guest-specific data (an open reservation, an in-progress incident, session state) never enters the package — it lives in the operational tables above and changes per-message; the package only changes when a tenant edits their config.

## 3. Runtime package compilation — resolved design

(Implemented in `logs/compile_runtime_package.py`, design decided 2026-07-22.)

1. **Trigger**: compile only on tenant config edit, not per guest message, not scheduled. Every run is currently a manual script invocation and is treated as an immediate publish (`published_at` set at insert time) — there's no separate draft/review gate for the whole package yet (only `response_templates.approval_status` gates wording today).
2. **Completeness**: no requirement. A `menu_options.next_branch_key` (or any other optional field) with nothing defined is simply left null — not an error.
3. **Referential integrity** (decided 2026-07-22, not yet implemented): anything that *does* have a value — `next_branch_key`, team references, etc. — must resolve to something that actually exists in the compiled set. Narrow, cheap existence check, not a full completeness/rules engine. Rationale: completeness-vs-integrity are separate questions; the completeness rule (#2) is right for where the project is, but silently allowing a *dangling* reference (a typo'd `next_branch_key` pointing at a branch that doesn't exist) risks a guest conversation stalling with nobody told there's a bug.
   - **Follow-up flagged, not yet built**: add a warning/flag surfaced somewhere (compile-time log, future mockup-tool UI) specifically so a broken reference doesn't fail silently — still needs a concrete design (where does the warning show up, who sees it) once the mockup tool exists.
4. **Versioning**: simple auto-incrementing integer (stored as text, per `runtime_packages.runtime_package_version`), assigned automatically by the compile script.
5. **Rollback**: no server-side package version history is consumed anywhere yet (though every compile run does insert a new row, so history exists for free). Primary rollback mechanism will be the future mockup tool letting a tenant download their own config as a file. Distinguish from *code* rollback, which is handled by the existing `dev`/`main` git branch separation.
6. **Compile logic**: a script, structurally the mirror of the seed script — reads Supabase config tables, writes one `package_json` blob. Manual today; automating "tenant clicks Publish" waits until the mockup tool exists.
7. **Package contents**: everything populated by the seed migration — property identity/settings, teams, venues (+ aliases + descriptions), reservation rules, menu branches/options/aliases/triggers, answer boundaries, runtime feature flags, response templates (both languages). No guest-specific data (per section 2).
8. **Generic graph-walker, confirmed** as the eventual replacement for `fast_path_classifier.js`/`fast_path_responder.js`'s hardcoded per-context `if` blocks, because tenants need to be able to add menu branches the code was never written to know about. **This directly conflicts with an earlier accepted v0.3 decision — see section 5's flagged conflict below, not yet resolved.**
9. **Caching**: webhook (once rewired) loads the package once, keeps it in memory, reloads only when a new version is published — falls out of #1.
10. **Cutover strategy**: big-bang swap of all 4 current JSON-load call sites, not an incremental parallel-run — acceptable given the `dev`/`main` branch safety net.
11. **Sequencing gate — met 2026-08-10 for the demo property.** `fast_path_classifier.js`/`fast_path_responder.js`/`property_loader.js` were rewired and live-tested with real WhatsApp traffic (see section 1). Not fully met in the original sense, though: "proven... with at least one tenant configured similarly to the demo property" implied a *second*, differently-shaped tenant — that still hasn't happened. Everything proven so far is against the one demo property's specific tree shape.

## 4. The future SOL Menu Runtime Service (not built, relevant once the gate in 3.11 is met)

Carried forward from the original `SOL_Menu_Runtime_Service_v0.3.md` proposal — this already sketches much of what a "generic graph-walker" needs to become and should be read before the actual rewrite, not re-derived from scratch.

Proposed request shape:
```json
{
  "property_key": "demo",
  "runtime_package_version": "2026-07-05.1",
  "session": {
    "current_language": "en",
    "fast_path_context": "restaurant_followup_menu",
    "selected_restaurant_key": "fenicia",
    "active_request_type": null
  },
  "input": { "raw_text": "2", "normalized_text": "2" }
}
```

Proposed response shape:
```json
{
  "handled": true,
  "result_type": "restaurant_followup_selection",
  "option_key": "new_reservation",
  "next_context": "restaurant_followup_menu",
  "template_key": "restaurant_new_reservation_prompt_en",
  "template_replacements": { "restaurant_name": "Fenicia" },
  "session_patch": { "selected_restaurant": "Fenicia", "active_request_type": "reservation" },
  "handoff": null,
  "reason": "context_lookup"
}
```

**Responsibilities**: context lookup, numeric/text/leading-choice resolution, list-trigger handling, back/menu/reset sentinel interpretation, next-context transition, template selection, venue carry-forward, branch stay/reprompt selection, deterministic handoff classification, invalid-input response.

**Explicitly not this service's job**: WhatsApp transport, Meta status processing, Voiceflow API transport, LOGS report generation, credential storage, tenant admin auth, free-form AI reasoning, DB table editing, final schema ownership.

**Still-open questions from that original proposal, unresolved**: internal module vs. separate HTTP service; which invalid inputs reprompt vs. fall through to Voiceflow/LLM; does template rendering happen in the service or the webhook/responder layer; is session patching advisory or authoritative. None of these need answers until the rewrite actually starts.

## 5. Tenant Property Configuration Tool (mockup tool) — scope

Carried forward from `Tenant_Property_Configuration_vs_Canonical_Schema_Gap_List_v0.3.md` (2026-07-05 review round, accepted at the time):

**Property-editable** (tenant-facing): venue display names, venue descriptions, venue hours, reservation rules/policy thresholds, response template wording, concierge name, default language, menu labels, service request slot labels, team display names, team scope text, and (as of 2026-07-28, see below) adding new teams.

**SOL/Admin-owned** (not tenant-editable): stable IDs and keys (`venue_key`, `team_key` — including for tenant-added teams, where the key is still system-generated as generic `team_N`, only the display name is tenant-chosen —, menu branch keys), runtime flags, tenant status, deployment secrets, webhook credentials. `dept_target` is no longer a real routing mechanism (see below) — it's a vestigial NOT NULL column nobody owns meaningfully anymore.

**✅ Resolved (2026-07-27)**: the 2026-07-05 v0.3 boundary ("keep full menu tree editing out of the tool," "menu structure should be SOL/Admin-owned") is **overridden**. Tenants get real menu-tree-authoring UI, scoped as follows:

- Each tenant starts from a generic tree structure modeled after the demo property's branch/option shape.
- Tenants can rename or remove any branch/option, and add new ones — including new top-level branches (new conversation categories), not just options within existing branches.
- The tree is bounded by a max depth and max children-per-branch, to protect graph-walker/back-navigation logic and WhatsApp's own interactive-list UI (which hard-caps at 10 rows). **Defaults: max depth 4 levels below `main_menu`, max 10 children per branch.**
- These limits are **SOL/Admin-owned, per-tenant configurable** — not a single global constant and not tenant-editable. A future product-owner control (not yet built) sets each tenant's ceiling; the tool enforces whatever ceiling is set, defaulting to 4/10 for new tenants. **Schema landed 2026-08-03**: `property_settings.menu_max_depth`/`menu_max_children_per_branch` (migration `20260803140000_add_menu_tree_limits.sql`), defaulted 4/10 and enforced live by the Menu Tree editor — the product-owner control to actually *set* a per-tenant ceiling is still unbuilt, but the columns it will write to now exist.
- **✅ Resolved (2026-08-03)**: the Menu Tree editor itself is built and live in `tenant_tool` — drill-down UI per branch (breadcrumb trail back to `main_menu`), add/rename/remove options, route a new option to a brand-new sub-branch or reuse one already targeted by a sibling option in the same parent (the only form of branch-sharing allowed, since it keeps `parent_branch_key` single-valued and depth well-defined — matches the real seeded pattern where `restaurants_menu`'s 7 venue options already all route to one shared `restaurant_followup_menu`). Deletion blocks until a routed-to sub-branch is empty, then cascades. Deliberately structure-only: `case_type`/`dept_target`/`template_key`/`target_file` untouched, since nothing consumes them yet (that's the queued incident/complaint write-path work). Full detail in the session handoff doc.

**✅ Resolved (2026-07-28): team routing is arbitrary per-tenant, not a fixed 3-value enum.** The original 3 teams' backend keys were semantically named (`fnb_team`/`sec_team`/`ops_team`) and routing (`dept_target`) was pinned to a fixed `check (dept_target in ('FNB','SEC','OPS'))` on both `teams` and `cases` — baked into `logs_app.py`'s 4 hardcoded routes/badges and `supabase_client.js`'s hardcoded write. Chosen resolution, given each tenant will eventually get their own LOGS login and isn't sharing routing buckets with anyone: **fully arbitrary per-tenant routing**, not shared fixed buckets.

- Migration `20260728120000_generalize_team_routing.sql` dropped both check constraints and renamed the 3 existing teams' keys to generic `team_1`/`team_2`/`team_3` (display names untouched).
- Real routing/display now runs entirely through `teams.team_key`/`display_name` and `cases.assigned_team_id` (an FK that already existed but nothing wrote to before this) — not `dept_target`, which stays only as a vestigial `NOT NULL` column auto-set to mirror `team_key`.
- `tenant_tool` can now add a team (`POST /teams/add` — computes the next generic `team_N` key, tenant supplies only the display name).
- `logs/`'s nav/routes/badges are now generated from the live `teams` table (`GET /team/<team_key>`) instead of 4 hardcoded views; per-case-type table columns (Location, Venue/Notes, Service Date) are shown for every view now rather than gated by which fixed department view you're on, since a team can no longer be assumed to mean one specific case type.
- ~~**Known gap, deliberately not solved here**: there is no per-venue routing data anywhere...~~ — **resolved 2026-08-03**: added `venues.handoff_team_id` (real FK to `teams.id`, not the old text-key idea), backfilled every venue to the Guest Services team (matching the old source JSON's own default), exposed as a live dropdown in `tenant_tool`'s Venues section, and wired into `supabase_client.js` so real reservation writes now resolve a venue's configured team instead of always landing `"unrouted"`. See `DB_Construction_Decisions_v0.1.md`.

This confirms the generic-graph-walker rewrite's stated justification (section 3.8) still holds. Full tradeoff discussion and the rejected alternatives (old boundary as-is; a hybrid allowing new options but not new branches) are recorded in `DB_Construction_Decisions_v0.1.md`.

Also still true from that review round, not superseded by anything since: menu lookup aliases, list triggers, response template governance fields (approval status), runtime feature flags, and the entire operational side (messages/cases/detail tables/events) were explicitly recommended to stay **out** of the wizard's v0.3 scope — worth re-confirming these are still out of scope now that tree-authoring is in scope, since that expands the tool's surface further than just menu branches.

## 8. Explicitly deferred / out of scope for now

Carried forward from `Tenant_Management_Future_Considerations_v0.1.md`, reconfirmed by everything since — do not act on these without a decision first:

- Tenant onboarding workflow (no tool exists to create a new tenant today).
- System administration workflow for SOL (approving tenants, user-count limits, roles, billing/subscription status — no billing concept exists anywhere in the schema).
- Per-tenant security / multi-user sub-accounts (no `users`/`tenant_users` table exists at all; no real Supabase Auth users exist for the webhook, LOGS, or the future mockup tool).
- Granular RLS policies for Property Admin / SOL Admin / LOGS-read roles — currently just `service_role` bypass + deny-all; per-role policies wait on those tools having real Auth users to scope against.
- Whether `tenant_id` needs to exist directly on every table (defense-in-depth) vs. scoping through `property_id` — currently inconsistent (operational tables carry both; config tables only carry `property_id`). Not urgent until real multi-tenant work begins.
- Voice/ElevenLabs channel support — modeled only as a future "channel and integration capability," not a property fact. No active implementation exists. Explicitly not to be overbuilt before the product path is approved.

- Typo/fuzzy venue matching — **partially resolved 2026-08-10**: the menu-selection → reservation handoff now uses a real `menu_options.venue_id` FK instead of fuzzy text matching. `webhook.js`'s other two free-text venue-matching sites (`extractReservationVenue`, `extractSingleVenueFromReply`, matching arbitrary guest text or a bot's LLM-generated reply) are untouched, deliberately out of this pass's scope.
- ~~Incidents/complaints never reach Supabase~~ — **resolved 2026-08-10.** `detectIntent` now distinguishes theft/safety signals (`case_type: "incident"`) from billing/service complaints (`case_type: "complaint"`) — previously both collapsed into `"complaint"`, so `incident_details` could never receive a real write. `writeCaseFromActiveRequest` (`supabase_bridge/supabase_client.js`) writes both, wired into the same exit-closure points `writeReservationCase` already used. Walking-skeleton content only (`summary` — see the LLM-generated-text item below); ships unrouted, same as reservations before `venues.handoff_team_id` existed. Verified live: a real "someone stole my wallet"-style conversation landed as `case_type: incident` in Supabase.
- **New, found live-testing 2026-08-10: mid-conversation reclassification.** `detectIntent` only classifies on a request's *first* message; once `active_request.type` is set, later turns don't re-evaluate even if the conversation reveals something different. Observed live: a guest's first message read as a billing complaint, classified `case_type: complaint`, but the conversation evolved into a real theft account ("kept the money and didn't give a car") — the case still wrote as `complaint`, not `incident`. Not a regression from this session's work (classification never re-evaluated before either), but a real, now-visible gap. Not sized or scoped yet.
- **Accidental team deletion protection — flagged 2026-07-29, not designed yet.** During this session's team-routing work, the repo owner nearly lost visibility into "Guest Services" (a team with 4 real assigned cases) via `tenant_tool`'s Delete button before the soft-delete-when-has-cases behavior existed — a native `confirm()` dialog was the only guard. Worth a real design pass before other tenants use this tool: options include requiring the tenant to type the team's display name to confirm (like GitHub repo deletion), a visible "recently removed teams" restore UI instead of relying on a developer running one-off Supabase queries to reactivate, or a short undo window after delete. Not urgent while this is single-tenant/dev-only, but should be resolved before real tenant users get access to Teams.
- **Response Templates / Answer Boundaries sequencing — decided 2026-08-04**: deferred to final edits, after the incident/complaint write path and the webhook rewire. Confirmed no rework risk in waiting: `compile_runtime_package.py` already reads both tables directly from Supabase and compiles them correctly with zero UI involved, same as every other config table before its own `tenant_tool` section existed, and nothing else built or planned depends on a tenant-editable UI existing for them. One open design question for whenever they are built, not urgent: `response_templates.approval_status` already gates what compiles (`compile_runtime_package.py:240` filters `.eq("approval_status", "approved")`) — everything is currently pre-seeded `"approved"`, a no-op today — whoever builds the edit UI needs to decide whether editing wording should flip it back to `draft`/`needs_review` as a real review gate, or save straight through like the rest of the tool does now.
- **`tenant_tool` rework pass — flagged 2026-08-04.** (1) How tenant-typed text actually reaches guests through `webhook.js` — spacing, emoji, and other formatting details in what a tenant types vs. what gets sent. **Partially resolved 2026-08-10** as a direct side effect of live testing: restaurant-list emoji were found missing and fixed (numbered emoji generated in code, per-venue emoji backfilled into `venue_descriptions` as real tenant-editable content, not a hardcode). No broader audit of tenant-typed-text fidelity done beyond that one concrete case. (2) Menu Tree subsections beyond structure-only scope — still not started. (3) Live previews — **built 2026-08-10** (see the Menu Tree entry-preview item above), though scoped only to Menu Tree; Response Templates/other sections still have none.
- **LLM-generated text vs. structured case fields — flagged 2026-08-04, found during first live test of the webhook rewire.** `writeCaseFromActiveRequest`'s `summary` now uses `session.last_bot_reply` (the LLM's own closing account of the complaint/incident, e.g. a real "Theft report — cash taken / Location: ... / Details: ..." message) instead of a fixed generic line — a cheap, free win since that text already exists in session state at write-time. This is still raw conversational text, not the structured `complaint_details`/`incident_details` fields (`category`, `severity`, `location_text`, `guest_impact`/`people_involved`) those tables actually have — parsing/transforming the LLM's own summary (or the fuller conversation) into those fields is real, unscoped follow-up work, distinct from and smaller than the "build a full accumulated-context object" option already declined in favor of the walking skeleton.
- **✅ Reservation `guest_name`/`special_requests` — resolved 2026-08-10, found in the same live-testing round.** A guest stated their name mid-reservation-conversation; it never reached the actual write. Root cause was bigger than a narrow heuristic: `vf_bridge/reservation_candidate_reader.js` is a whole second, more reliable extraction path (Voiceflow's own LLM-based reading of `guest_name`/`notes`/etc.), explicitly scoped in its own header as **"PHASE 1 — READ AND LOG ONLY: NO merge into governed middleware state"** — built, but never wired to anything. "Phase 2" (`webhook.js`'s VF-bridge block) now merges `guest_name` into `session.guest_profile` (preferred over the old `extractGuestName` prompt-heuristic) and `notes` into `reservation_context.special_requests`, finally reaching `reservation_details.special_requests` — previously hardcoded to always `null`. `contact_phone` deliberately left alone: there's an existing, working phone-reuse-confirmation flow this must not bypass. Verified live: a real reservation captured "Jerry Steinberg" and his phone number correctly.
- **✅ Menu Tree read-only entry preview — built 2026-08-10.** Each branch's Menu Tree page now shows, in one card right under the breadcrumb, what a guest actually sees *arriving at that level* — not what any individual option inside it leads to next (an earlier version of this previewed per-option instead, corrected same day before shipping: "the preview is a level above what it should be... it should show the configuration of the layer you are viewing, not the layer within it"). Sourced by finding the entry option (the option in the parent branch whose `next_branch_key` routes here — same lookup `_branch_label` already used for breadcrumbs) and rendering its `template_key` via `response_templates`, with venue substitution for venue-linked entries; `main_menu` sources directly from `main_menu_prompt`. A read-only Python mirror of `buildBranchEntryReply`/`buildOptionReply` in `fast_path_responder.js` (kept in sync by hand, documented as such; drift only shows a wrong preview, never breaks a guest conversation, since it writes nothing). No entry template resolving shows a visible "⚠️ No response configured for this level" warning. Surfaced directly in the card, not hidden: this is static template text, not generated from the option labels below it — editing a label here does not update it. That gap is exactly what motivated the next queued item below.
- **✅ Per-branch intro/fallback message — resolved and built 2026-08-10.** Directly caused by the entry-preview item above surfacing how many options (especially any new one a tenant adds) have no configured response at all. Scoped decision-by-decision before any code was touched (see `Next_Session_Handoff_2026-08-10.md`'s follow-on session for the full trail):
  - New nullable `menu_branches.fallback_template_key text` column (migration `20260810120000_add_menu_branch_fallback_template.sql`), a soft reference into `response_templates` — same non-FK pattern as `menu_options.template_key`, chosen specifically so the still-unbuilt Response Templates `tenant_tool` section will transparently be able to edit this content too, with no bespoke editor ever needed for it.
  - **Real finding while scoping this, correcting a wrong assumption in this doc and in `fast_path_responder.js`'s own header comment**: `GENERIC_FALLBACK_TEMPLATE` was never actually reachable from `webhook.js` (`buildResponse` is only ever called inside `if (fastPathResult)`, and its own `!result` branch — the only path that returns that string — is therefore dead code from that call site). The true existing behavior for *any* unconfigured branch/option, before this change, was a silent fall-through to Voiceflow's own AI, not a generic string. That's the actual default this feature overrides.
  - `fast_path_responder.js`: `buildOptionReply` now takes a `branch` param — its `fallback_template_key`, if set, stands in (per language) whenever the option's own resolved template is missing, before falling through to Voiceflow. Applies uniformly to both branch-entry (`buildBranchEntryReply`, including `main_menu`) and a plain in-branch option selection — one rule, not two special-cased paths. For branch-entry specifically, the fallback owner is the branch being *arrived at*, not the parent branch the routing option structurally lives in (a real fork surfaced and resolved during scoping — the "per-branch intro" framing only makes sense if arriving at level X shows level X's own configured intro). No inheritance: an unset branch always falls through to Voiceflow regardless of what any ancestor has configured, matching how `template_key` already has no inheritance anywhere else in this schema.
  - Ships with **column + wiring only, no seed content**: checked live before deciding this — 49 of 50 existing options already have `template_key` set, the one exception (`room_service`) is inactive, so there is no current gap to backfill. Every branch starts unset (identical to pre-existing Voiceflow-fallback behavior) until someone sets one.
  - `tenant_tool`'s Menu Tree entry preview (`_option_preview`/`_branch_entry_preview` in `app.py`) updated to mirror the same per-language fallback merge, and now shows a second read-only line alongside the existing "⚠️ No response configured" warning, stating whether that branch's `fallback_template_key` is set — informational only, since no UI to set it exists yet.
  - **Flagged, not built**: no `tenant_tool` UI to set `fallback_template_key` exists yet (same authoring gap as the rest of `response_templates`). Explicitly noted for whenever Response Templates editing is built: the Menu Tree page itself is expected to eventually host setting *this specific* per-branch field directly (it's naturally part of viewing a branch), rather than requiring a trip to a separate Response Templates screen — distinct from general template-wording editing, which stays in its own section.
- **✅ `reservation_details.reservation_name` never written — resolved 2026-08-24, found live-testing the fallback deploy.** `writeReservationCase` captured `guest_name` for `cases.guest_name` but never wrote it to `reservation_details.reservation_name` (a real schema column). One-line fix in `supabase_bridge/supabase_client.js`.
- **✅ `venues.show_in_restaurant_list` was fully inert — resolved 2026-08-24.** Compiled into the runtime package but never read by the fast-path classifier or responder, so toggling a venue off (intended use: closed for remodeling, without deleting it) had no guest-facing effect. Now wired via a new shared module (`src/fast_path/visible_options.js`) so the classifier and responder can't drift on numbering; hidden venues are excluded from the list, numeric matching, and label/alias matching, with the remaining options renumbering contiguously. See section 1 for the full account, including a second bug this surfaced (stale legacy numeric aliases in `menu_option_aliases`, also fixed the same day).
- **Flagged 2026-08-24, not built: Voiceflow has no venue-availability guardrail.** A guest typing a hidden venue's name by hand bypasses the fast-path classifier's (correct) refusal and reaches Voiceflow as plain text, which has no awareness of `show_in_restaurant_list` and will process a full reservation for it anyway — confirmed live (Larry's Sports Bar & Terrace, hidden for "remodeling," still got a reservation flow going via the AI path). Candidate mechanism: `webhook.js` already injects bracketed context into the Voiceflow payload for other things (`[[RESTAURANT CONTEXT: ...]]`), and the same approach could carry current venue availability. Needs its own scoping pass: what exactly gets injected, when, and how it interacts with a venue the guest already picked earlier in the conversation. Not started.
